== Step 4: block-streaming schedule (capacity-wall regime) ==
== Expand each instance in subtree blocks of 2^b leaves (double-buffered block
== region, rows 512+); MAU drains block j-1 inside block j's deepest window.
== Leaf footprint: 2 x 2^b x 16B instead of 2 x 2^n x 16B -> unlocks the W
== cells (N=2^24, t<=8) where the flat leaf buffer exceeds one bank.
== n=14, I=256, 64ch, 8r8w cl=272, gated. Op counts validated exactly
== (blocked = flat + underfilled shallow block levels: +1.6% ops @b=10).
==
n=14 flat mau (baseline)      cycles=2780571 ACT=157455 ns/leaf=0.4143
n=14 block=2^10 (16 blocks)   cycles=2659723 ACT=248256 ns/leaf=0.3963  (-4.3%)
n=14 block=2^12 (4 blocks)    cycles=2672743 ACT=266797 ns/leaf=0.3983  (-3.9%)
n=14 expansion-only floor                                ns/leaf=0.3827
==
== VERDICT: block-streaming is NOT an overhead -- it is FASTER than the flat
== schedule. Mechanism: the flat schedule's per-instance MAU drain is one big
== block (128 ops) that the finite request queue semi-serializes (the +8.3%
== over the floor); blocked cuts it into 16 small drains that genuinely hide
== inside the next block's window (+3.6% over floor). ACT is HIGHER (248k vs
== 157k, block-region row ping-pong) yet time is lower -- issue granularity,
== not ACT count, is what costs time (third time this lesson appears).
== Consequences:
==  1. W cells in the superiority map are CONSERVATIVE, not optimistic: the
==     schedule those cells require is faster than the 0.401 flat constant.
==  2. Blocking should be adopted everywhere, not just at the wall (candidate
==     PIM_NS_LEAF: 0.396; kept at 0.401 flat in models = conservative).
==  3. Blocked windows are small (<=64 ops/ch) -> large-n direct simulation
==     becomes tractable again (the superlinear sim-cost problem was the flat
==     schedule's giant windows, not physics).
